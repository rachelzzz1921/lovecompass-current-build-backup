## 一、处理原则

本轮按用户新增约束执行：**项目不从零开发，不整仓复制开源项目，只复用成熟模块或成熟设计模式**。对于附件中的 P0/P1 工具清单，我采用“先查重、再轻量试用、最后记录跳过理由”的方式处理。所有涉及 Supabase 与 AI 的密钥均继续遵守既有安全边界：服务端密钥只进入本地 `.env` 或未来 Vercel Environment Variables，不进入源码、模板、文档或浏览器 bundle。

> 结论：本轮实际新增采用的是 **Vercel AI SDK 核心包、OpenAI-compatible provider、NanoID**。Supabase 与 Recharts 已在项目中存在或已接入，继续沿用。Prisma、Upstash Redis、Langfuse、Refine、PostHog、Sentry 暂不安装，原因是它们要么与当前后端形态冲突，要么依赖外部账号/密钥，要么属于后台或监控阶段，不适合在当前 Supabase 真库联调前强行引入。

## 四、为什么没有按附件“严格顺序”全部安装

附件建议的开发顺序以 Next.js 单体项目为默认前提，而当前 LoveCompass 已经存在 **Lovable/Vite 前端 + FastAPI 独立后端 + SQL migration** 的半成品架构。如果此时按附件一次性安装 Prisma、Redis、Langfuse、Refine、PostHog、Sentry，会产生两类问题。第一，Prisma 会与既有 SQL migration 和 Python 后端形成重复数据模型，增加迁移风险。第二，Redis、Langfuse、PostHog、Sentry 都需要额外平台注册或项目 Key，当前用户明确要求缺少注册项时要先说明，因此这些项应延后到对应阶段。

因此，本轮只采用能立即降低开发风险且不改变主架构的成熟模块：**AI SDK 用于统一模型接口，NanoID 用于安全 ID/兑换码生成，Vercel AI Chatbot 仅作为聊天流和消息结构参考**。

## 五、下一步建议

下一步仍应优先补齐 Supabase 真库联调缺口。当前已经有 Supabase URL、anon JWT 与 service role JWT，但还需要 `DATABASE_URL` 或数据库密码来执行迁移和题库导入。完成真库迁移后，再把兑换码生成工具接入后端兑换码批量生成接口，并把 AIAdapter 接入实际聊天 API 的 SSE 输出路径。
