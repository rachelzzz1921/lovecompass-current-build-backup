# LoveCompass 四系统模块复用映射方案

作者：**Manus AI**  
日期：2026-05-23

## 一、结论摘要

LoveCompass 后续应继续沿用现有 Lovable 前端与 FastAPI 后端骨架，不从零开发，也不复制任何参考项目整仓代码。参考项目的价值在于帮助我们确定 **模块边界、数据流、接口契约和可演进工具栈**。其中，Formbricks 适合作为测试系统的数据模型参考，Vercel Chatbot 与 Vercel AI SDK 适合作为 AI 系统的聊天、SSE、模型适配参考，react-admin 适合作为后台系统的资源管理参考，而兑换码系统应保留 LoveCompass 自有业务逻辑，但后台管理接口可以按 react-admin 的 Data Provider 模式暴露。

> Vercel Chatbot 将自身定位为基于 Next.js 与 AI SDK 的开源聊天模板，并包含数据持久化、聊天历史、用户数据、文件存储和多模型路由等能力；这适合作为 LoveCompass AI 系统的结构参考，而不是整仓复制对象。[1]

## 二、四个业务系统的模块边界

| LoveCompass 系统 | 参考来源 | 复用的成熟模式 | 不复用的部分 | 当前落地优先级 |
|---|---|---|---|---|
| 测试系统 | Formbricks | Survey/Question/Response 拆分、问题配置、答案记录、PostgreSQL 数据组织 | 多租户体验管理、复杂投放规则、完整 Formbricks 产品后台 | 最高，先完成 Supabase 真库迁移和题库导入 |
| AI 系统 | Vercel Chatbot、Vercel AI SDK | 聊天消息表、SSE 流式响应、模型 provider 抽象、多模型路由、环境变量纪律 | 整套 Next.js Chatbot UI、AI Gateway 默认绑定、Neon/Vercel Blob 强依赖 | 高，先保留 `AIAdapter.generate(prompt)`，再补流式与智谱实现 |
| 兑换码系统 | 自有业务为主，后台借鉴 react-admin | 兑换码 CRUD、状态筛选、批量生成、使用记录追踪 | 外部支付或订单系统的重型实现 | 高，支撑测试解锁和 MVP 变现闭环 |
| 后台系统 | react-admin | Resource、Data Provider、标准 CRUD、筛选排序分页 | 复杂企业权限包、过早接入全量后台生态 | 中，先设计管理 API，后接 admin UI |

## 三、测试系统：参考 Formbricks，但保持 LoveCompass 题型契约

Formbricks 文档将 **Survey** 定义为问卷的中心模型，并将 **Response** 用于记录用户答案，这与 LoveCompass 的 `test_suites`、`test_questions`、`attempts`、`attempt_answers` 拆分高度一致。[4] 因此测试系统不需要重做，而应在现有数据库迁移上继续推进：题库仍由 `test_suites` 与 `test_questions` 管理，作答会话仍由 `attempts` 表承载，答案明细仍由 `attempt_answers` 保存。

| Formbricks 概念 | LoveCompass 对应实体 | 说明 |
|---|---|---|
| Survey | `test_suites` | 一套测试，例如男性版、女性版或后续关系版测试 |
| Question | `test_questions` | 题目本体，包含题型、选项、滑杆、评分配置 |
| Response | `attempts` | 一次完整答题会话，关联用户、测试、兑换码和结果状态 |
| Response Data | `attempt_answers` | 每题答案，保留原始答案与归一化答案，便于重新评分和 AI 分析 |

当前前端已经实现统一 `QuestionRenderer`，应继续坚持这一方向。不同题型只映射到 Lovable 已设计好的展示组件，不为每一种题单独写页面。后端 API 只返回标准化问题契约，由前端自然匹配单选、多选、滑杆、排序、场景题等呈现模式。

## 四、AI 系统：保留轻量 Adapter，逐步引入流式能力

Vercel AI SDK 的官方介绍强调其目标是标准化不同 AI 模型提供商的接入，并提供 AI SDK Core 与 AI SDK UI 两层能力，其中 Core 面向文本生成、结构化对象、工具调用和 Agent，UI 面向聊天与生成式界面。[2] 这一理念与用户提出的 `AIAdapter.generate(prompt)` 完全一致。

| AI 能力 | 当前 LoveCompass 状态 | 参考项目模式 | 建议下一步 |
|---|---|---|---|
| 模型统一接口 | 已有 Python `AIAdapter.generate(prompt)` | Vercel AI SDK provider 抽象 | 暂不新增 SDK；等智谱 Key 和真实生成需求明确后补 `ZhipuProvider` |
| 聊天消息管理 | 已有聊天接口骨架和表设计 | Vercel Chatbot 消息持久化 | 新增 `chat_sessions` 与 `chat_messages` 的读写封装 |
| SSE 流式响应 | 暂未实现 | Vercel Chatbot / AI SDK UI streaming | 在 FastAPI 增加 `/chat/stream`，前端保留普通接口 fallback |
| 多模型切换 | 目前仅预留智谱 | AI SDK 多 provider 路由 | 设计 `AI_PROVIDER=zhipu|mock|openai_compatible`，不要把模型写死 |

当前不建议马上引入 Vercel AI SDK 到现有前端，因为现有项目不是 Next.js App Router，而是 Lovable/TanStack 风格前端加独立 FastAPI 后端。若未来迁移到 Next.js 或把聊天 API 放到 Vercel Serverless Functions，则可以重新评估 AI SDK 作为 TypeScript 侧 Adapter 的底层实现。

## 五、兑换码系统：自有业务模型优先，后台使用 Resource 思路

兑换码系统是 LoveCompass 的商业闭环，不能直接从参考项目套用。它的核心不是问卷，也不是聊天，而是 **权益解锁、使用次数、有效期、绑定 attempt、后台生成和审计**。因此后端仍应保留现有 `redemption_codes` 设计，并新增可管理的 admin API。

| 功能 | API 建议 | 后台资源名 | 备注 |
|---|---|---|---|
| 验证兑换码 | `POST /api/redemption-codes/verify` | `redemption_codes` | 用户端使用，返回是否可进入测试 |
| 批量生成 | `POST /api/admin/redemption-codes/bulk-create` | `redemption_codes` | 后台使用，可按套餐、渠道、有效期生成 |
| 查询状态 | `GET /api/admin/redemption-codes` | `redemption_codes` | 支持筛选、排序、分页 |
| 使用记录 | `GET /api/admin/redemption-code-usages` | `redemption_code_usages` | 追踪 code 与 attempt/user 关系 |

## 六、后台系统：参考 react-admin Data Provider，不先造复杂后台

react-admin 文档明确 Data Provider 是后台前端与 API 之间的接口层，并通过 `getList`、`getOne`、`create`、`update`、`delete` 等方法映射到后端 API。[3] 因此 LoveCompass 后台系统的正确顺序不是先做 UI，而是先让后端 admin API 具备标准资源语义。

| react-admin 方法 | 后端 API 约定 | LoveCompass 资源示例 |
|---|---|---|
| `getList` | `GET /api/admin/{resource}?sort=&range=&filter=` | 题库列表、兑换码列表、作答记录列表 |
| `getOne` | `GET /api/admin/{resource}/{id}` | 单题详情、单个兑换码、单次作答详情 |
| `create` | `POST /api/admin/{resource}` | 新增题目、新增兑换码 |
| `update` | `PUT /api/admin/{resource}/{id}` | 编辑题目、禁用兑换码、修正测试配置 |
| `delete` | `DELETE /api/admin/{resource}/{id}` | 删除草稿题、废弃兑换码 |

后台系统可以后置，但 admin API 的命名应从现在开始按资源方式规划，以避免后期为 react-admin 重写接口。

## 七、工具栈决策

| 工具 | 当前是否引入 | 原因 | 需要用户协助吗 |
|---|---:|---|---|
| Supabase | 是，正在接入 | 数据库、认证和后续部署环境都需要真实落地 | 还需要 Supabase URL、数据库连接串或数据库密码；已给出的密钥会只进入 `.env` |
| Vercel | 暂不本地依赖，部署前接入 | 用户已指定临时上线链接走 Vercel | 部署前需要 Vercel 项目与环境变量配置确认 |
| Vercel AI SDK | 暂不新增依赖 | 当前后端是 FastAPI，先保留轻量 Python Adapter；若迁移 Next.js AI API 再引入 | 暂不需要 |
| react-admin | 暂不新增依赖 | 先把 admin API 设计成资源化，UI 后续接入更稳 | 暂不需要 |
| Prisma | 暂不新增依赖 | 当前已有 SQL 迁移和 Python/FastAPI 骨架；若切 Next.js 全栈或 react-admin 数据层再评估 | 暂不需要 |
| Formbricks | 不作为依赖 | 只参考 Survey/Response 数据模型，不嵌入产品代码 | 不需要 |

## 八、后续执行顺序

接下来应先完成 Supabase 安全接入与真库迁移准备，然后基于四系统边界调整后端目录和 API 命名。AI 侧继续保留 `AIAdapter`，但将 provider 配置从代码中抽出到环境变量。后台侧先补 admin API 契约文档，不立即安装 react-admin。这样可以做到 **用成熟项目校准架构，但不让项目被外部模板牵着走**。
