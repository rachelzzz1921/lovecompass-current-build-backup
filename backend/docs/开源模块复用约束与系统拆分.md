# LoveCompass 开源模块复用约束与系统拆分

作者：**Manus AI**  
日期：2026-05-23

## 一、已冻结的实施原则

LoveCompass 后续开发不从零重写，也不复制整套开源项目。当前前端已经由 Lovable 完成主要呈现设计，后续工程工作应以 **成熟模块复用、接口模式借鉴、业务层适配** 为主。所有外部项目只能作为架构、数据模型、接口边界和成熟实现模式的参考，不能直接整仓搬运，也不能引入与当前业务不匹配的大型复杂度。

| 原则 | 执行方式 | 禁止事项 |
|---|---|---|
| 不从零开发 | 继续保留 Lovable 已完成的页面、题型呈现和跳转体验，在现有代码上接入真实 API | 推倒重写整个前端或后端 |
| 只复用成熟模块 | 参考成熟项目的模块边界、数据结构、接口和运行机制 | 为了“高级”而引入未验证或过重依赖 |
| 不复制整个项目 | 按 LoveCompass 业务需要抽取思想和局部模式 | 直接把参考仓库整套代码合并进项目 |
| 按业务拆解 | 以测试系统、AI 系统、兑换码系统、后台系统组织实现 | 混成一个难维护的大接口或大组件 |
| 密钥安全优先 | 所有密钥只走 `.env` 和部署平台环境变量，服务端密钥不进入浏览器代码 | 将 service role、数据库连接串或 AI Key 写死到源码、文档或公开仓库 |

## 二、参考项目与对应业务系统

| 参考项目或工具 | 主要借鉴点 | 对应 LoveCompass 系统 | 当前处理方式 |
|---|---|---|---|
| `vercel/ai-chatbot` | 聊天消息管理、SSE 流式响应、多模型对话结构 | AI 系统 | 后续只参考消息表、流式接口和模型路由，不整仓复制 |
| Vercel AI SDK | 统一模型接口、provider 抽象、流式生成 API | AI 系统 | 当前 Python 后端已有 `AIAdapter.generate(prompt)`；如切到 Next.js 服务端或需要 SSE，可再评估引入 |
| `react-admin` | 后台资源管理、列表/编辑/权限模式 | 后台系统 | 后台作为独立 admin 子系统设计，不影响用户端测试流程 |
| Formbricks | 问卷/调查数据结构、问题类型、答案结构 | 测试系统 | 当前题库契约已对齐 `question -> options/scale/scoring` 思路，后续可继续参考其调查模型 |

## 三、四个业务系统的边界

| 系统 | 核心职责 | 主要实体 | 首要落地点 |
|---|---|---|---|
| 测试系统 | 题库展示、题型渲染、作答提交、结果生成入口 | `test_suites`、`test_questions`、`attempts`、`attempt_answers` | 已有 Lovable 前端和 FastAPI 契约，下一步联调 Supabase 真库 |
| AI 系统 | 分析报告生成、聊天、模型切换、上下文管理 | `ai_jobs`、`chat_sessions`、`chat_messages`、模型配置 | 已有 `AIAdapter` 占位，后续补 SSE 和智谱真实调用 |
| 兑换码系统 | 兑换码验证、购买后解锁、使用次数和过期控制 | `redemption_codes`、兑换记录、订单或套餐 | 当前已有验证接口骨架，后续需要后台生成与批量导入能力 |
| 后台系统 | 题库管理、兑换码管理、用户/作答/AI 作业查看 | Admin resources、权限角色、审计日志 | 后续参考 `react-admin` 资源模型独立实现 |
