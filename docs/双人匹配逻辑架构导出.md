> 导出时间：2026-05-27  
> 用途：供外部评审（Claude 等）分析「双人匹配逻辑」是否合理、如何优化  
> 范围：**套三 MATE 婚恋适配**（主）+ **套二 ROS 关系合测**（对照）

## 0. 核心问题摘要（评审入口）

产品里存在 **两套不同的「匹配」语义**，容易混淆：

| 语义 | 触发时机 | 引擎 | 输出 |
|------|----------|------|------|
| **单人匹配区间** | 做完 MATE 80 题单人测评 | `mate_match_bounds.py` | `upperMatch` / `sweetSpot` / `lowerMatch` —— **假设型**对象画像（「什么样的人对你算上限/甜区/下限」） |
| **双人婚恋适配** | 双方均完成 MATE full + 补充题，用关系码配对 | `mate_couple.py` | P1–P6 模块 + 综合分 `verdict.score` —— **真实两人**对比 |

**评审重点建议：**

1. 单人区间的 P1–P6 权重与双人引擎是否应一致？（目前单人用 `compute_pair_compatibility_base`，双人用 `aggregate_score`，公式相近但输入不同）
2. 双人 P4（长期规划）高度依赖 **14 道补充题**；未填完时 P4 退化为 P3 分数，是否导致分数虚高/虚低？
3. `extract_profiles` 强制按 male/female 分桶，initiator/partner 性别若与桶不一致时的 fallback 逻辑是否可靠？
4. P5 风险是 **规则命中 penalty**（越高越差），聚合时用 `(100 - P5.score)` —— 与单人 `build_match_bounds` 里 `P5 = 100 - risk` 是否对齐？
5. 单人结果页「匹配区间」与双人结果页「现实适配分」数字体系不同，用户是否会困惑？

## 7. 单人评分 + 匹配区间（MATE Single）

### 7.1 模块与坐标

文档：`backend/docs/套三_MATE择偶坐标体系_V1.0.md`  
实现：`backend/app/mate_scoring.py` + `mate_engine.py`

**女版 FS1–FS5 / 男版 MS1–MS5**，算出：

- `axisX` 市场显示度
- `axisY` 现实支撑力
- `positionType` 六种定位（如「让人想留下来的人」）

### 7.2 单人匹配区间引擎

文件：`backend/app/mate_match_bounds.py`  
词库：`backend/data/mate_match_bounds_v1.json`

**步骤：**

1. `compute_pair_compatibility_base` —— 从 **单人** module_scores 推导 P1–P6 基准分
2. `base = P1×0.30 + P2×0.25 + P3×0.15 + P4×0.15 + P5×0.10 + P6×0.05`
3. 按 `position_name` + `gender` 查 `bounds_by_position` 配置
4. 输出三分区：`upperMatch` (+5分 adjust)、`sweetSpot` (0)、`lowerMatch` (-5 - risk×0.08)
5. 每区挂载 **虚构人物画像** `portraits[]`（来自 JSON 库）

**女版 P 映射（单人基准）：**

```
P1 = axisY×0.55 + FS3×0.45
P2 = FS2
P3 = FS4
P4 = axisY×0.45 + FS4×0.55
P5 = 100 - FS5
P6 = FS1
```

**男版 P 映射（单人基准）：**

```
P1 = axisY×0.55 + MS1×0.45
P2 = MS3
P3 = MS2
P4 = axisY×0.45 + MS2×0.55
P5 = 100 - MS5
P6 = MS4
```

写入：`mate_scoring._build_mate_result_payload` → `result_payload.upperMatch/sweetSpot/lowerMatch`

## 8. 双人婚恋适配引擎（MATE Couple）

### 8.1 核心文件

| 文件 | 职责 |
|------|------|
| `backend/app/mate_couple.py` | P1–P6 计算、payload 组装 |
| `backend/data/mate_pair_model_v1.json` | 模块权重、P5/P6 规则 |
| `backend/data/mate_couple_copy_v1.json` | 文案、badge 规则、verdict 模板 |
| `backend/app/mate_pair_supplement.py` | 补充题解析 → fields |
| `backend/app/mate_couple_ai_content.py` | AI 润色 action_item / texture |

### 8.2 六模块定义（双人）

来自 `mate_pair_model_v1.json`：

| 模块 | 名称 | 双人计算逻辑（摘要） |
|------|------|---------------------|
| **P1** | 现实条件适配 | `100 - abs(male.reality - female.reality)`；reality: 男 MS1 / 女 FS3 |
| **P2** | 情感需求适配 | 男 MS3 vs 女 FS2 对齐分 |
| **P3** | 相处节奏适配 | 男 MS2 vs 女 FS4 对齐分 |
| **P4** | 长期规划适配 | 补充题：城市/生育/住房/时间等；**无数据时 fallback = P3** |
| **P5** | 风险碰撞 | 规则引擎命中 penalty（越高越险）；如双向拉扯、边界冲突、家庭介入 |
| **P6** | 火花增益 | 规则引擎 bonus；P5 高时 dampening |

**综合分：**

```python
score = P1×0.30 + P2×0.25 + P3×0.15 + P4×0.15 + (100-P5)×0.10 + P6×0.05
```

### 8.3 extract_profiles 分桶逻辑

```python
# 每人按 gender 放入 profiles["male"] / profiles["female"]
# derived 字段：
#   男: density=MS3, stability=100-MS5, reality=MS1, ...
#   女: density=FS2, stability=100-FS5, reality=FS3, ...
# 补充题 fields: age, education, huji, want_children, city_plan, ...
# 单人题映射: 学历/收入/住房/事业/家庭 → context 展示字段
```

### 8.4 输出 payload 结构（MATE_PAIR_V4）

```json
{
  "model": "MATE_PAIR_V4",
  "engine": "MATE_PAIR_ENGINE_V1.0",
  "code": "ROS-XXXX-XXXX",
  "participants": { "youGender", "taGender", "youPosition", "taPosition", ... },
  "verdict": { "score", "title", "oneliner", "desc", "texture?" },
  "modules": { "P1": { "score", "level", "atoms" }, ... },
  "condition_table": [...],
  "deal_items": { "highlight": [...], "dim": [...] },
  "rhythm": [...],
  "attention": [...],
  "conclusion": { "summary", "items", "action_item?", "ai_pending" },
  "supplementComplete": bool,
  "youSupplementComplete": bool,
  "taSupplementComplete": bool,

}
```

### 8.5 P5 规则示例（JSON 驱动）

```json
{
  "id": "mutual_pull",
  "when": { "all": [
    { "ref": "male.scores.MS5", "op": "gte", "value": 60 },
```

## 14. 已知逻辑张力点（供优化讨论）

### 14.1 两套「匹配分」并存

- 单人页：`sweetSpot.matchScore`（假设对象，来自自身模块推导）
- 双人页：`verdict.score`（真实两人 P1–P6）
- **用户可能期望**：双人分 ≈ 与「最合拍」画像相遇的分数 —— 当前 **无此映射**

### 14.2 P4 对补充题依赖

```python
# mate_couple.compute_P4
if not alignments:
    p3 = compute_P3(male, female)
    score = p3["score"]  # 无补充题 → P4 = P3
```

未做补充题时，长期规划模块 **复制相处节奏分**，可能高估「可谈婚论嫁」。

### 14.3 P1 现实适配仅用模块分差距

- 未直接使用收入/住房 **补充题** 做 P1（只在 condition_table 展示）
- P1 的 reality：女 FS3、男 MS1 —— 与「收入水平」行（来自单人题 label）可能 **不一致**

### 14.4 性别分桶 edge case

```python
male = profiles.get("male") or profiles.get(_gender(partner if _gender(initiator) == "female" else initiator))
```

同性别配对（若产品允许）会逻辑混乱 —— 当前产品假设 **异性恋二元**。

### 14.5 MATE vs ROS finalize 差异

- ROS：link 后 try `merge_and_store_couple_report`
- MATE：link 后不 merge，等首次 GET couple

可能导致伴侣完成后发起人 **不能立即** 在 analyzing 流里 prefetch 双人报告（需手动进 couple 页）。

### 14.6 单人 match bounds 的 P6

单人 `compute_pair_compatibility_base` 含 P6，但 **未参与** `base` 加权（只到 P5）；双人 `aggregate_score` **含 P6×0.05** —— 权重模型微差。

## 15. 给 Claude 的评审问题清单
